# FUSE v0.7.0 Release Notes

## Release theme

**FUSE v0.7.0 focuses on SST plugin backend conformance and acceptance testing.**

This release adds a backend-only SST external-validation harness owned entirely by the SST plugin. The harness improves confidence that SST JSON generated by FUSE is not only structurally valid, but can also be checked against real SST tooling when the developer or CI environment is configured for it.

## Architectural boundary

All new SST-specific conformance logic lives under the SST plugin:

```text
fuse/plugins/community/sst/external_validation/
fuse/plugins/community/sst/tests/test_sst_external_validation.py
```

Nothing about this harness is added to FUSE core or core tests. Core remains plugin-agnostic, while the SST plugin owns SST JSON export validation, SST fixture metadata, SST element/component checks, SST init/runtime execution, and any `sst-ext-tests`-inspired behavior.

## Highlights

### SST plugin external-validation harness

v0.7.0 adds a structured backend harness for generated SST acceptance fixtures. The harness can run the following ladder:

```text
SST plugin fixture/model builder
  -> SST export-readiness validation
  -> SST JSON export
  -> JSON syntax check with python -m json.tool
  -> expected SST JSON contract checks
  -> optional SST element/component availability checks with sst-info
  -> optional sst --run-mode=init
  -> optional runtime smoke execution
  -> optional expected stdout/stderr/output-file checks
```

The harness produces structured result objects for each stage so failures and skips can be reported clearly in tests and CI logs.

### Backend-only pytest marker

External SST acceptance tests use the `sst_ext` marker:

```bash
cd ~/research/fuse/fuse
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q -m "sst_ext"
```

The harness is skipped by default unless explicitly enabled:

```bash
export FUSE_ENABLE_SST_EXT_TESTS=1
```

This keeps normal development and user workflows lightweight while allowing deeper SST validation in release or CI environments.

### Rich fixture metadata

Acceptance fixtures now describe their own requirements using SST plugin metadata, including:

- fixture name and description
- minimum and maximum SST version bounds
- required SST element libraries
- required SST components
- run mode: `json`, `init`, or `run`
- timeout and expected return code
- runtime arguments
- expected stdout/stderr fragments
- expected generated output files
- external-suite tags for future filtering or interoperability

The metadata is validated before fixture execution so invalid or contradictory fixture definitions fail early.

### SST version and dependency-aware skips

The harness can detect and skip fixtures cleanly when the current machine does not satisfy a fixture's requirements.

Supported checks include:

- `sst` availability
- `sst-info` availability
- SST version bounds
- required element libraries
- required components

This distinction matters because a fixture may be valid but still not runnable on a particular developer machine if the required SST Elements library is not installed.

### Generated fixture coverage

v0.7.0 adds representative generated SST fixtures, including:

| Fixture | Run mode | Coverage |
|---|---|---|
| `minimal_two_component_link` | `json` | Basic component/link export contract and top-level JSON structure. |
| `explicit_latency_parameters` | `json` | Typed parameters, empty-parameter omission, stable names, and asymmetric endpoint latencies. |
| `subcomponent_slot_assignment` | `json` | Native SST SubComponent nesting and slot-name export. |
| `simple_element_example_init` | `init` | Real-SST init path using `simpleElementExample` when available. |

Fixtures are generated through the SST plugin acceptance helpers and real SST JSON exporter rather than being treated as hand-written output artifacts.

### Runtime-smoke support

The harness supports optional runtime-mode fixtures for small simulations that are expected to terminate quickly. Runtime checks can verify:

- expected process return code
- stdout fragments
- stderr fragments
- generated output files

Runtime-mode fixtures remain opt-in and should be used only for stable, small SST models.

### Optional `sst-ext-tests` interoperability root

v0.7.0 adds optional recognition of:

```bash
export SST_EXT_TESTS_ROOT=/path/to/sst-ext-tests
```

This is only an interoperability/developer-diagnostics hook. FUSE does not vendor `sst-ext-tests`, does not require it for normal tests, and does not treat its current test corpus as the complete definition of valid SST behavior.

## Testing

The SST plugin external-validation tests cover:

- external-validation enable/skip behavior
- metadata validation
- JSON syntax checking
- SST init command construction
- SST runtime command construction
- expected stdout/stderr/output-file checks
- SST element availability checks
- SST component availability checks
- SST version-bound handling
- optional `SST_EXT_TESTS_ROOT` validation
- generated fixture export acceptance
- generated fixture suite reporting
- representative generated fixture contracts

Run the targeted backend harness tests with:

```bash
cd ~/research/fuse/fuse
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q \
  plugins/community/sst/tests/test_sst_external_validation.py
```

Run the marker-based external suite with:

```bash
QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q -m "sst_ext"
```

Enable real SST execution stages with:

```bash
FUSE_ENABLE_SST_EXT_TESTS=1 QT_QPA_PLATFORM=offscreen \
  .venv/bin/python -m pytest -q -m "sst_ext"
```

## Known limitations

- The harness is a backend/release validation tool, not a user-facing feature.
- JSON-mode fixtures prove export and contract shape, but do not prove real SST runtime behavior.
- Init/runtime fixtures depend on the local SST/SST Elements installation.
- Component availability checks depend on `sst-info` output and may need refinement as more SST elements are covered.
- The `sst-ext-tests` interoperability hook validates the root path only; deeper bidirectional integration remains future work.
- Runtime/golden checks should be added cautiously for small, stable models to avoid flaky CI behavior.

## Summary

FUSE v0.7.0 strengthens the SST plugin's backend confidence story. The SST plugin now owns a structured acceptance harness that can prove representative FUSE-generated SST JSON fixtures validate, export, initialize, and where practical run under real SST tooling, while keeping all SST-specific conformance logic out of FUSE core and invisible to normal users.
